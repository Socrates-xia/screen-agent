# 设计说明与实测记录

本文件记录 screen-agent 的关键技术决策及其**实测依据**，
供后续维护时判断"哪些地方不能乱改"。

---

## 一、坐标系：为什么四者能对齐

目标：让「UIA 报告的坐标」「截图的像素坐标」「Win32 API 的坐标」「点击落点」完全一致。

**做法**：进程启动时立刻声明 `Per-Monitor V2 DPI 感知`，然后全程只用物理像素，
不做任何逻辑像素换算。

**顺序很关键**：`core/__init__.py` 在导入任何 UI 库之前先调用 `dpi.setup()`。
若被 `uiautomation` 抢先（它在 import 时会调用 `SetProcessDpiAwareness(PerMonitor)`），
则 PMv2 无法再设置，本机 150% 缩放的主屏会产生 1.5 倍坐标偏差。
这也是为什么**必须通过 `sa.py` 入口调用**，不要绕开它单独 import 子模块。

**实测（自建 Win32 窗口）**：

```
UIA 窗口坐标   = [120, 120, 640, 480]
Win32 GetWindowRect = [120, 120, 640, 480]   ← 完全一致
按钮中心点     = btn-alpha [266,242] / btn-beta [266,322] / btn-gamma [266,402]
截图采样像素   = mss 与 GDI GetPixel 逐点 Δ=0
```

## 二、三个必须记住的坑

### 坑 1：`MOUSEEVENTF_ABSOLUTE` 的归一化空间是「主显示器」

**现象**：SendInput 用绝对坐标移动光标，X 坐标**精确减半**，Y 完全正常。

```
目标(300,300) -> 实际(150,300)   偏差(-150,+0)
目标(500,350) -> 实际(250,350)   偏差(-250,+0)
目标(900,600) -> 实际(450,600)   偏差(-450,+0)
```

**原因**：按虚拟桌面宽度 5120 归一化，但系统按**主显示器宽度 2560** 解释。
本机是双屏 2560+2560 拼接，所以恰好差 2 倍；若两块屏分辨率不同，
偏差会表现为更复杂的小数比例，更难察觉。

**解法**：移动光标改用 `SetCursorPos`（直接吃物理像素，双屏实测零偏差）；
点击用 `SendInput` 只发 `DOWN/UP`（不带 `MOVE` 标志），作用于当前光标位置。

**实测（SetCursorPos）**：

```
(60,60)      -> (60,60)      跨主屏左上
(2560,800)   -> (2560,800)   主副屏交界
(5060,800)   -> (5060,800)   副屏远角
(3000,500)   -> (3000,500)   副屏
```

### 坑 2：WinUI/XAML 应用的 UIA 坐标不可信

**现象**：Win11 记事本的标签页，UIA 返回 `(-5616,791)-(-5536,823)`
—— 屏幕外负坐标，而该窗口实际位于 `(3045,781)`。

**解法**：每个元素都过 `dpi.rect_in_virtual_desktop()` 校验，
不合格标记 `plausible=False`，`click` 会拒绝执行并提示改用 OCR。

### 坑 3：Chromium/Electron 的控件树是异步构建的

**现象**：首次向 Chrome/Electron 窗口请求 UIA 时返回空树（accessibility 尚未启动）。

**解法**：`scan_window()` 内置重试 —— 扫到空就先等，再扫；实测 Harness
（Electron）首次扫描即成功拿到 40 个元素（标签页、按钮、菜单项）。

## 三、为什么点击前要做「点下元素身份复核」

这是本技能最重要的安全机制。

**问题**：会话里存的是「扫描那一刻的坐标」。以下情况会让坐标指向别的东西：

| 情况 | 后果 |
|---|---|
| 列表滚动 | 同一个 (x,y) 现在指向另一个列表项 |
| 标签页切换 | 原位置换成了功能完全不同的按钮 |
| 窗口被遮挡 | 点击穿过目标窗口打到遮挡物上 |
| 窗口移动 | 坐标整体偏移 |

粗体的是最危险的：**在不可撤销的界面上（删除、确认支付、提交）会直接造成损失。**

**三层防护**（`session.resolve_target()`）：

1. **屏幕布局校验** —— 虚拟桌面尺寸变了直接拒绝
2. **点下元素身份复核**（`uia.verify_point()`）—— 用 `ControlFromPoint` 查
   该点当前是什么元素，与记录比对，返回五种结论：
   `match` / `ancestor` / `occluded` / `mismatch` / `unknown`
3. **整窗重扫重定位**（`uia.relocate()`）—— 复核不通过时按
   `(类型, 名称, AutomationId)` 在窗口内重新查找

**实测**：

```
未被遮挡的元素         -> match      → 放行
被遮挡的元素           -> occluded   → 拒绝，提示"请先 activate"
resolve_target 结论    -> ok=False, reason="目标已被其他窗口遮挡…"
```

## 四、已知的能力边界

| 场景 | UIA 是否能识别 | 说明 |
|---|---|---|
| Win32 / WPF / WinForms | ✅ 完整 | 最可靠 |
| Electron / Chromium | ✅ 需预热 | 已内置重试 |
| WinUI 3 / XAML | ⚠️ 坐标可能异常 | 靠 `plausible` 校验拦下 |
| Qt（如微信 PC 版） | ❌ 常返回空 | 实测微信窗口扫描结果 = 0 个元素 |
| 游戏 / 全屏 DirectX | ❌ | 需 OCR 或专用方案 |
| 远程桌面画面 | ❌ | 画面是位图，无控件树 |
| Java / Swing | ⚠️ 部分 | 取决于是否开启辅助功能桥 |

**微信这类 Qt 应用扫不出元素，是 OCR 兜底存在的直接原因。**

## 五、性能参考（本机实测）

| 操作 | 耗时 |
|---|---|
| 截全屏 5120×1600 并保存 PNG | **590 ms** |
| 单窗口 UIA 扫描（156 个元素） | **674 ms** |
| `ControlFromPoint` 点下复核 | **5 ms** |
| OCR 识别 700×900 区域（rapidocr，33 个文字块） | **2527 ms** |

**关于最后两行**：

- 点下身份复核只要 **5ms**，比一次"重扫整个窗口"（674ms）便宜两个数量级。
  因此它在 `resolve_target()` 里被放在**最前面**作为默认快路径 ——
  用极小的成本换掉最高频的一类误点风险。这是刻意的工程取舍，勿轻易改成"先重扫"。
- OCR 成本高一个数量级，且随面积增长（全屏可达数十秒）。所以它只作**兜底**
  （UIA 拿不到控件树时才用），并**建议用 `--region` 限定区域**。

会话默认 180 秒过期，避免用陈旧坐标盲点。

## 六、修改代码时的注意事项

- **不要**把 `SetCursorPos` 换回 `SendInput` 绝对坐标移动（见坑 1）
- **不要**在 `dpi.setup()` 之前 import `uiautomation` / `mss`（见第一节）
- **不要**放宽 `plausible` 校验（见坑 2）
- **不要**在 `click` 路径上跳过 `verify_point`（见第三节）
- **不要**在 `resolve_target` 的「重新定位」分支里放行 `occluded`（见第三节与第十四节）
- **不要**把 `hotkey` / `press` / `click` / `drag` 的抬起动作挪出 `finally`
  （见第十四节）——一次异常就能把 Ctrl 卡在用户机器上
- 改完务必跑：`python -B scripts/tools/selftest.py`（无交互桌面时加 `--quick`）

## 十四、安全加固：把"建议"变成"机制"

这一节记录 2026-10 的加固改动。起因是一个认识：**安全不能只写在提示词里。**
"请先 dry-run"是对一个可能忽略指示的模型说的，因此真正的护栏必须是代码。

### 坑 4：重新定位路径曾放行 `occluded`

**现象**：第三节的三层防护中，快路径正确拒绝了 `occluded`，但慢路径
（`resolve_target` 的重定位分支）只检查 `mismatch` 就置 `ok=True` ——
`occluded` 与 `unknown` 会一路放行并真的点下去。

**为什么危险**：重定位恰恰发生在**界面已经变化**的时候，而这正是目标
最容易被别的窗口盖住的时刻。等于在最需要防护的分支上把防护关掉了。

**修法**：慢路径执行与快路径**完全相同**的判定集合，并对 `unknown` 追加
`strict` 门槛。这条已加入第六节的"不要"清单。

### 坑 5：异常会把修饰键留在按下状态

**现象**：`hotkey` 原本是"依次 key_down，然后逆序 key_up"。若在按下阶段
抛异常（目标窗口中途消失、`SendInput` 失败），key_up 循环永远不执行。

**后果**：Ctrl 物理卡在按下状态，用户之后敲的每个字符都变成快捷键，
直到手动敲一次 Ctrl 才恢复。这比"点击失败"严重得多。

**修法**：`keyboard.py` 维护 `_held_keys` 集合，`_key_up` 先摘除再发送；
所有按下/抬起序列包在 `try/finally` 里；并提供 `release_all()` 作为应急兜底。
`mouse.click` / `mouse.drag` 同样处理（鼠标键卡住会让整机无法正常点击）。

### 坑 6：双击间隔不能写死

**现象**：`double_click_time()` 定义了却无人调用，`click()` 用写死的 0.09s。

**为什么危险**：用户在「鼠标设置」里调快双击速度后，所有 `--count 2` 都会
退化成两次独立单击 —— 静默失败，且极难定位原因。

**修法**：`_safe_gap()` 以 `GetDoubleClickTime()` 的 40% 为上限动态计算。

### 坑 7：角落热区保护用错了坐标系

**现象**：`_corner_guard` 用 `SM_CXSCREEN`/`SM_CYSCREEN` 的 width/height
当绝对坐标去判断"是否在主屏右下角"。

**为什么危险**：这两个值是**相对主显示器原点**的尺寸。副屏插到主屏左侧时
主屏原点变成 (2560, 0)，保护就会守错矩形 —— 或者守了个空，等于没有。

**修法**：新增 `dpi.primary_rect()` 返回主屏的**绝对**矩形
（来自 `EnumDisplayMonitors` 的 `primary=True` 那一条），保护逻辑改用它。

### 坑 8：`--dry-run` 会真的把用户的光标拖走

**现象**：`dry_run=True` 时依然调用了 `move()`，光标被拽到目标点后留在那里。
而 SKILL.md 恰恰把 `click --id --dry-run` 推荐为**首选演练方式** ——
被推荐的安全动作，是唯一会乱动鼠标的动作。

**修法**：演练结束默认把光标移回原位（`keep_cursor=True` 可保留）。

### 新增机制一览

| 机制 | 位置 | 作用 |
|---|---|---|
| 不可逆操作闸门 | `core/safety.py` | 元素名/窗口标题命中删除·支付·提交等词时默认拒绝（退出码 4），需 `--yes` |
| 词边界匹配 | `safety._matches` | ASCII 词按词边界匹配，避免 `kill` 命中 `Skill` |
| 锁屏检测 | `safety.is_locked` | `OpenInputDesktop` 失败即判定锁屏，拒绝输入（退出码 3） |
| 审计日志 | `safety.audit` | append-only `audit.jsonl`，含被拦截的记录；`sa.py audit` 查看 |
| 双通道真兜底 | `keyboard.type_text` | 传入 `verify_fn` 时读回校验，不通过自动降级剪贴板重试 |

> 关于双通道：原先文档承诺"两条通道互为兜底"，但 `auto` 是无条件走 unicode，
> 没有任何回退逻辑 —— 文档描述了代码里不存在的安全网。现在兜底依赖**读回校验**，
> 因为 unicode 通道最危险的失败模式是 `SendInput` 成功但应用根本不认
> UNICODE 事件（内容静默丢失），只看返回值发现不了。
> 这也是为什么 `type` 命令默认**不**开启校验：没有校验时降级会导致重复输入。
> 需要严格场景请显式指定 `--method clipboard`。

## 七、OCR 引擎的集成细节

**引擎**：`rapidocr` 3.9.2 + `onnxruntime`，模型为 PP-OCRv6（det/rec small）
加中文方向分类器，全部离线运行，模型随包就位（无需运行时下载）。

**交叉验证**：对屏幕左侧 700×900 区域做 OCR，识别出的
「新建任务 / 助理 BETA / 专家·技能·连接器 / 定时任务 / 资料库 / 更多」
与同一区域 UIA 扫描得到的元素名称**高度一致**（置信度多为 1.00），
说明两条通道互不矛盾、可互为佐证。

**必须静音的坑**：RapidOCR 初始化时会向 **stderr** 输出大量 INFO 日志
（形如 `[INFO] ... [RapidOCR] base.py:23: Using engine_name: onnxruntime`），
不清除会污染输出。处理方式见 `core/ocr.py::_silence()`：
`logging.disable(logging.INFO)` 全局屏蔽 INFO 及以下（保留 WARNING/ERROR 以免掩盖真实故障），
再对名字含 `rapid`/`ocr` 的 logger 关闭 handler，并在调用期间重定向 stdout 兜住直接 print。

## 八、键盘：为什么必须双通道

**问题**：虚拟键码（VK）只能表达 ASCII 范围内的按键，「中」「输」这类汉字没有对应的 VK。
用 `KEYEVENTF_UNICODE` 直接投递 UTF-16 码元可以绕过输入法，但**部分应用不认**
（老式控件、部分游戏、某些远程桌面场景）。

**方案**：两条通道，互为兜底（`core/keyboard.py`）

| 通道 | 实现 | 适用 |
|---|---|---|
| `unicode`（默认） | `SendInput` + `KEYEVENTF_UNICODE`，`wScan` 填码点 | 记事本、浏览器、Electron —— 快，无需剪贴板 |
| `clipboard` | 写剪贴板 + `Ctrl+V`，用完恢复原内容 | 对 UNICODE 事件不友好的应用 |

BMP 之外的字符（emoji）会拆成代理对分两次发送（`_unicode_units`）。

**实测**：两种通道输入 `Hello 中文输入 123` / `剪贴板通道` 后从控件读回，
内容与原文完全一致。

## 九、拖拽：为什么必须拆成多步

**问题**：只发一次「按下 → 瞬移到终点 → 松开」，应用收到的是**一个跳跃的位置变化**，
不会进入拖拽状态 —— 会被当成一次普通点击。

**方案**（`core/mouse.py::drag`）：

1. 移动到起点 → **按下** → **hold_before（默认 0.14s）** 再开始移动
   （很多应用要等一小会儿才进入拖拽态）
2. 把位移拆成 `steps` 段（按距离自动估算，约 12px 一步，上限 120），
   每步 `SetCursorPos` + 小延时，用 smoothstep 缓动使起止更自然
3. 到达终点后 **hold_after（默认 0.16s）** 再松开，让目标应用完成 drop 判定

**实测**：应用侧收到 **30 次连续 mousemove、累计位移 370px**（起点 30 次 = 29 步插值）。

**★ 一个真实的坑（调试了半小时）**：拖拽**起点若落在子控件（按钮/输入框）上，
父窗口根本收不到 `WM_LBUTTONDOWN`** —— 消息被子控件拿走了。
排查时用 `mouse.click` 点所谓"空白区"却命中了 `btn-gamma` 才暴露出来：
窗口 `GetWindowRect` 是**外框**，客户区从 `(131,165)` 才开始（不是 `(120,120)`），
我按外框推算的空白点实际压在按钮上。**算客户区必须用 `GetClientRect` + `ClientToScreen`。**

**不适用于滑块验证**：本函数生成的是直线轨迹，图形验证码的风控会识别为机器人。
滑块类人机验证一律交给人（见 `core/human.py`）。

## 十、浏览器：为什么走 UIA + 快捷键，而不是 Playwright/CDP

用户要操作的是**自己那个已经登录了各种账号的 Edge**。三条路对比：

| 方案 | 登录态 | 是否需重启浏览器 | 能力 |
|---|---|---|---|
| **UIA + 快捷键**（本技能采用） | ✅ 完全保留 | ❌ 不需要 | 标签/导航/地址栏/点击元素/读文字 |
| Playwright 新实例 | ❌ 全新干净环境 | — | 强，但等于从零开始 |
| CDP 接管现有实例 | ✅ | ✅ 必须以调试端口重启 | 最强（可执行 JS） |

选了 UIA 路线：零配置、不动用户会话、登录态原样保留。
代价是拿不到 DOM、不能执行 JS —— 需要那些能力时应改走 CDP。

**实现要点**：
- 标签栏的识别：取窗口**顶部 9% 区域**内的 `TabItemControl`，按 x 排序，
  以过滤掉页面内部同名的 tab 控件
- 当前标签的判定：用 UIA 的 **`SelectionItemPattern.IsSelected`**。
  一开始用「窗口标题字符串匹配」猜，但多标签时窗口标题会被改写成
  「某标题 和另外 N 个页面」，根本匹配不上，导致所有标签都被标记为当前。

## 十一、前台锁定：`SetForegroundWindow` 会被拒绝

**现象**：`browser open` 报"无法激活浏览器窗口"。`SetForegroundWindow` 调用成功返回，
但窗口并没有到前台，只有任务栏图标闪了一下。

**原因**：Windows 的前台锁定策略 —— 非前台进程不能随意抢占前台。

**解法**（`core/uia.py::_force_foreground`）：`AttachThreadInput` 把本线程的输入队列
临时附加到当前前台窗口所在线程，从而取得设置前台的权限。这是 Windows 官方认可的
标准做法，不是 hack。兜底还有「最小化→还原」破除前台锁。

**安全设计**：`activate()` 返回**是否真的成为前台窗口**。所有要发键盘的操作
（`browser *` / `type`）都先检查这个返回值，失败就**拒绝执行** ——
宁可报错，也绝不能把 `Ctrl+W` 之类发到错误的窗口上。

## 十二、人工介入检测：为什么需要它

自动化最怕的不是失败，而是**自以为成功**。遇到登录页/验证码时继续照旧点击，
轻则点空，重则触发风控或误提交。

**三层检测**（`core/human.py`，由快到慢）：

| 层 | 手段 | 成本 | 能发现 |
|---|---|---|---|
| ① 窗口标题 | 字符串匹配 | ~0 | "验证码 - Google Chrome" 这类明显的 |
| ② UIA 文本 | 扫控件名 | ~2s | 按钮/标签文字，以及**密码输入框**（`IsPassword`）、"验证码"输入框 |
| ③ OCR | 识别屏幕文字 | 数秒 | 自绘界面、Canvas、游戏 |

`mode=auto`：前两层无结论时才跑 OCR，兼顾速度与召回。

**评分分级**：特征词带权重（10=几乎必然人工 / 4=很可能 / 1=仅参考），
累加后 `≥10 → high`、`≥4 → medium`、`≥1 → low`。只有 high/medium 才算"需要人工"，
避免页面里出现"登录"二字就误报。

**实测**：窗口标题设为 `请输入验证码 - 安全验证` → level=high（score 28，
命中"验证码/请输入验证码/安全验证"）；设为 `请拖动滑块完成验证` → level=high；
恢复为正常标题 → level=none、score=0，**不误报**。

## 十三、修改代码时的注意事项（补充）

- 键盘操作前**必须**确认目标窗口已激活（`activate()` 返回 True），否则按键会乱飞
- 拖拽的起点要避开子控件（见第九节）
- 给浏览器发的每个快捷键都有副作用（`Ctrl+W` 会关标签），改动 `browser.py` 时
  保持"失败即中止"的模式，不要图省事跳过激活检查
- 新增人工介入特征词时，权重按"是否几乎必然需要人来做"给，宁可少给也别滥给
  （误报会让 Agent 频繁无谓地打断用户）
